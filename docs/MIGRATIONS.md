# AAOS Protocol Migrations

AAOS schemas carry a `protocol_version` field (currently `"1.0"` in all five schemas: `agent-registry`, `task`, `handoff`, `event`, `heartbeat`). Per the project's Non-Goals, there is no compatibility-matrix or negotiation machinery — this file is the entire versioning mechanism, plus the `protocol_version` field itself.

**Rule:** `tools/validate.py` rejects any AAOS file whose `protocol_version` major version does not match the current supported major version, with an error message pointing here.

**How to bump the protocol version:** when a schema needs a breaking change, (1) increment the major version (e.g. `1.0` → `2.0`) in the relevant schema's `const`, (2) add a dated entry below describing exactly what changed and why, (3) update `tools/validate.py`'s supported-version check, (4) if existing state files need to keep working, write a one-off migration note here describing the field-by-field transformation — there is no automated migration tooling in v1; this is a manual, documented process by design.

## Version history

### 1.0 — 2026-07-09 (initial)
Initial release of all five schemas (`agent-registry`, `task`, `handoff`, `event`, `heartbeat`) as part of AAOS Phase 1. No prior version exists; nothing to migrate from.

## CLI behaviour changes (no protocol_version bump)

### 2026-10-17 -- A0.5: CLI input validation (audit M03, M43 behaviour part)
The queue CLIs now reject invalid inputs with exit 2 *before* any lock, lease, event or state is touched:

- `--now` must carry a UTC offset in all seven queue CLIs (`lease-task`, `expire-leases`, `complete-task`, `create-task`, `emit-event`, `fail-task`, `post-handoff`). A naive value (e.g. `2026-07-09T12:00:00`) now exits 2 with `USAGE ERROR: --now: ...`; previously it was accepted and compared against timezone-aware datetimes. `expire-leases` also now reports a bad `--now` as exit 2 instead of an uncaught exception.
- `lease-task --ttl-min` must be an integer >= 1; `lease-task` and `expire-leases` `--skew-min` an integer >= 0; `lease-task --settle-sec` a finite number >= 0 (NaN and Inf rejected). A negative `--skew-min` previously let a contender reclaim a still-live foreign lease.
- The ratified defaults are unchanged (45-minute TTL, 5-minute skew, 30s settle) and are defaults, not floors: `--settle-sec 0` and `--skew-min 0` remain valid.

### 2026-10-17 -- A0.5 follow-up (code-review findings)
- `publish-notion.py --now` now goes through the same tz-aware parser: a naive or unparseable value exits 2 with `USAGE ERROR: --now: ...` before any request is built or sent. Previously the raw string became the Notion page-title timestamp.
- Numeric flags gained loose SANITY ceilings so absurd values fail as usage errors (exit 2) instead of an `OverflowError` (exit 1) or a decades-long `sleep` while holding a lock: `--ttl-min` and `--skew-min` <= 525600 (one year); `--settle-sec` <= 3600. These are not policy; the real lease-TTL ceiling is ADR-0006 D3 (`LEASE_TTL_CAP`, not yet implemented) and will replace the `--ttl-min` ceiling.
- `lease-task.py` now rejects `--settle-sec` >= `--ttl-min` x 60 (exit 2, naming both flags). The lock's `expires` is stamped before the settle sleep, so a settle that lasts as long as the lease left the holder asleep while its own lock was already reclaimable, and the conflict path could then archive a legitimate reclaimer's live lock. The defaults (30 s settle, 45-minute TTL) are unaffected.
- `--now` must also fall in years 1970-9000. An extreme year made later `now +/- timedelta(...)` arithmetic raise `OverflowError` (exit 1 'UNEXPECTED ERROR') instead of a usage error.
- `publish-notion.py` writes the validated `--now` back with `datetime.isoformat()`, so non-canonical inputs are normalized in the page title (`...Z` becomes `...+00:00`, a space separator becomes `T`).
- Callers to check: any recipe or scheduled-task command line that passes a naive `--now` or a zero/negative value. The scheduled `ora-aaos-expire-leases` sweep runs `expire-leases.py --project ora-ops` with defaults only, so it is unaffected; verify with one supervised run after merge.

### 2026-10-17 -- event drain: a read error never quarantines a valid event (independent-review finding)
- `drain_event_spool` used to move a pending event file to `pending/_corrupt/` on ANY `OSError` while reading it (a OneDrive or antivirus sharing violation is the everyday cause). Nothing reads `_corrupt/`, so a valid event vanished from every view. It now retries a few times inside the drain and then leaves the file in `pending/` (warning names the file); the next drain retries it. While the read error lasts, `read_events` cannot read the file either, so readers (`fail-task`, the projection) do not see that event until it becomes readable: it is deferred, not lost. A file cut off in the middle of a multi-byte UTF-8 character (a half-synced file) is now quarantined instead of retried; cut-off ASCII JSON already was.
- A pending file that is not valid UTF-8 used to raise `UnicodeDecodeError` out of `drain_event_spool` and `read_events`, so one such file (it sorts first) wedged every later drain and crashed every reader. It is now quarantined to `_corrupt/` like other malformed files, and `read_events` skips it.
- Files that were read and are malformed JSON, not an object, or lack `event_id` are quarantined exactly as before.

### 2026-10-17 -- event drain and read_events: review fixes on the read-error change above
- `read_events` now reads pending files through the same bounded-retry helper as the drain, so a briefly locked file (antivirus / OneDrive) is retried instead of silently skipped. If it is still unreadable after the retries, `read_events` prints `WARNING: read_events could not read pending event file <name> ...` to stderr and omits that event from that one call (not lost: it stays in `pending/`). Callers (`fail-task`'s DoubleFailure check, the projection) emit that warning to the process's stderr; none of them capture or act on it, so a still-locked `Failed` event leaves the DoubleFailure view incomplete (tracked as a follow-up).
- The in-drain retry is now 3 attempts with 0.05s then 0.1s backoff (<= 0.15s per stuck file, was ~10ms total).
- Grace window (`QUARANTINE_GRACE_SECONDS = 600`): a pending file that is not valid UTF-8 or not parseable JSON is treated as possibly half-synced and left in `pending/` with a warning while its mtime is within 600s of now; it is quarantined only if still bad after that. This supersedes the earlier line above that a file cut inside a multi-byte character is quarantined at once: within the window it is now deferred. Complete JSON that is not an object or lacks `event_id` is still quarantined at once. A genuinely corrupt old file is still quarantined and still never wedges the drain.
- A pending file with a leading UTF-8 BOM is now accepted (decoded as `utf-8-sig`) instead of quarantined as malformed JSON.
- The quarantine warning is now truthful: if creating `_corrupt/` or moving the file fails, it says `could not move ... left in pending/` instead of `moved to`, and that failure no longer aborts the drain (valid events behind the bad file still fold).
- A deferred event folds into the NDJSON after events with later timestamps; NDJSON order is append order. `read_events` sorts by timestamp, so readers are unaffected.

### 2026-10-17 -- timestamps: a trailing 'Z' parses the same on every Python (L0 probe finding)
- Cowork's sandbox runs Python 3.10, and `datetime.fromisoformat` only accepts a trailing `Z` from 3.11. On 3.10 that made `_parse_iso_dt` raise, `parse_cli_now` reject a valid `--now`, and `read_events` silently sort Cowork's `Z`-stamped events last (reversing their order against local-offset events). `_parse_iso_dt` now rewrites a `Z` that directly follows a digit to `+00:00` before parsing, so a `Z`-stamped value with a 0, 3 or 6 digit fraction parses the same on 3.10, 3.11 and 3.13. Nothing that 3.11+ rejected is newly accepted (a lowercase `z`, a doubled `ZZ`, a bare `Z`, a naive value). **That alone did not make 3.10 agree with 3.11+.** A differential fuzz (about 507,000 strings; 3.11 and 3.13 agree exactly) found that 3.10 rejected shapes 3.11+ accepts: a fraction of 1, 2, 4, 5, 7, 8 or 9+ digits (PowerShell and .NET write 7; `date +%N` writes 9), an offset without a colon (`+0000`, `-0400`; the L0 probe's own `date -u +%FT%T%z` writes `+0000`) or without minutes (`+00`), and the comma decimal. On 3.10 such a value made `parse_cli_now` exit 2 and `read_events` sort that event last, silently. `_normalise_iso_for_py310` (applied only below 3.11) now rewrites a full `YYYY-MM-DD<sep>HH:MM:SS[.f][offset]` stamp (any one-character separator, as 3.11+ allows, so a lowercase `t` works) into the shape 3.10 accepts: the fraction padded or truncated (not rounded) to 6 digits, the offset as `+HH:MM[:SS]`, a `Z` after a dot as `+00:00`. Verified against CPython 3.13 as oracle: 0 disagreements in that family over an 82,592-string differential on 3.10, 3.11 and 3.13, no previously accepted value changed, and 3.11+ behaviour is untouched. **Still different on 3.10** (outside the family; the normaliser returns them unchanged so nothing 3.11+ rejects is newly accepted): whitespace before the offset or `Z` (3.13 accepts it only for some fraction lengths), an offset with a seconds fraction (`+05:30:15.5`), times without seconds followed by a colon-less offset, and basic, week and ordinal formats. 3.10 also still accepts a few things 3.13 rejects, such as `...:23Z+00:00`; that was already true and is not widened.
- CI now also runs Python 3.10, Cowork's interpreter (measured 3.10.12).
