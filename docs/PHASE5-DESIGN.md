## New scenario designs

### #2 — Corrupt task file, queue otherwise unaffected
Seed 3 tasks: two well-formed (`t-scn2-ok-a`, `t-scn2-ok-b`), one hand-truncated to invalid JSON (`t-scn2-corrupt`). Run `tools/validate.py` against all three — assert the two well-formed ones pass, the corrupt one fails loudly (non-zero exit, clear parse-error message naming the file). Then run `tools/lease-task.py` against `t-scn2-ok-a` — assert it succeeds normally (the corrupt sibling file caused zero interference). Separately, attempt `lease-task.py` against the corrupt task itself — assert it fails closed with a clear error (via `_aaos_common.load_task`'s `CorruptStateError` path) rather than crashing with a raw traceback or, worse, silently treating malformed content as valid.

### #4 — Seam unavailable
Using `--seam-root` pointed at a path that does not exist (simulating the OneDrive sync folder being unmounted/renamed), run each of: `create-task.py`, `lease-task.py` (against a pre-seeded task id, seam absent), `post-handoff.py`, `complete-task.py`, `expire-leases.py`. Assert every one fails closed — non-zero exit, a clear "seam unreadable"-class message (via `UsageError`/`FileNotFoundError` surfacing, not a raw unhandled traceback) — and that no file is created anywhere (in particular, no partial task/lock/event file appears if the parent directory structure gets auto-created by `atomic_write`'s `os.makedirs` before the read that would have failed — check this ordering specifically, since `atomic_write`'s directory-creation could theoretically succeed even when the seam "root" itself is absent, which would be a partial, misleading side effect worth flagging if found).

### #8 — Partial write / interrupted sync leaves the prior version intact
Write a valid `task.json` (v1, schema-valid, some recognizable field value). Directly construct the exact `atomic_write` sequence by hand to simulate an interruption: write a `.tmp-<pid>` file with truncated/incomplete v2 content, then **do not** perform the `os.replace` (simulating the process dying between the write and the rename — the realistic OneDrive-sync-fault or killed-process scenario `atomic_write` itself is specifically designed to make impossible in the normal path). Assert: the live `task.json` still contains v1 byte-for-byte, `tools/validate.py` against it still passes, and the stray `.tmp-*` file is detectable (list the directory, confirm its presence) as evidence a human/sweep could notice and clean up (per OPERATIONS.md's new guidance, added this phase — see below). This proves the *design's* claim (no tool ever writes a state file in place; a crash mid-write can't corrupt the live file) empirically, not just by code inspection.

### #10 — Rollback drill on an in-flight (leased) task
Create a fresh task, actually lease it for real (`lease-task.py`, real settle — or `--settle-sec 0` to keep the drill fast, noting that's a test-only override, not a claim about the production timing), confirming a live lock file now exists. Then execute the OPERATIONS.md §3 archive procedure **as documented, exactly** — but first confirm the doc's procedure correctly calls for archiving the lock too (an in-flight task has one; the existing §3 step 3 already lists "any lock file still present," written generically — this drill is what proves that generic wording is actually sufficient for the leased case, not just the already-completed case it was originally validated against). After archiving: assert (a) `tasks/_archive/<id>.json` exists, `state:"archived"`, and validates; (b) the lock no longer exists at its live path (moved to `locks/_archive/`); (c) **the event log is untouched** — the `TaskCreated`/`TaskLeased` events for this task remain exactly where they were, in place, and no new event was fabricated to describe the manual archive (per §3's own "leave the event log alone" rule — the master prompt's own "no side effects" framing is satisfied by history staying complete and unedited, not by pretending nothing happened); (d) no dangling reference anywhere else (no other task/handoff still points at this task id in a way that would now resolve to a missing live file).

## OPERATIONS.md additions this phase

A new `§5 — Failure-mode quick reference` maps each of the ten scenarios to either an existing section (§1-4 already cover #1, #6, #9's detection via §1's validate-anything step, #10) or a new short paragraph for the gaps: recognizing and recovering from a corrupt task file (#2 — point at §1's validate-first discipline plus: don't guess-fix, archive the corrupt file to `_archive/` with a `.corrupt` marker and recreate the task fresh if the content is unrecoverable, never hand-repair JSON you can't fully verify); what "seam unavailable" looks like operationally and the correct response (#4 — every tool already fails closed on it; the human action is fixing the seam/OneDrive sync, not working around the tools); a one-line pointer for the stale-Notion-mirror case (#5 — already covered narratively in §1, cross-reference only); recognizing and cleaning up a stray `.tmp-*` file from an interrupted write (#8 — safe to delete once confirmed the corresponding real file is intact and valid, since a `.tmp-*` file was, by construction, never the live state); and what a write-scope-violation error means and how to fix it (#9 — usually a wrong `write_scope` entry in `agent-registry.json`, not a bug in the handoff itself — check the registry before assuming the artifact path is wrong).
