# AAOS V2 Backlog

Design questions and extensions that surfaced during Phase 1 architecture work — legitimate future work, explicitly out of scope for v1. Each entry states why it's deferred, not just that it is.

1. **Lease auto-renew piggybacked on heartbeat.** v1 has no lease renewal at all: it is specified (AAOS-SPEC.md §7) but UNBUILT, and no `--renew` flag or renew tool exists in `tools/`. Auto-renewing a lease while its holder is known-alive is deferred behind that: the 45-minute TTL already covers every job length observed in this environment, and auto-renew would couple the health-monitoring chain to the lock manager in a way not yet justified by real need.

2. **Second-project onboarding runbook.** The path convention (`projects/<project-id>/...`) already supports multiple projects, but only one — `ora-ops` — is seeded in v1. The concrete runbook for onboarding a second project (registry `write_scope` additions, a new Notion view, sweep scoping) is deferred until a real second project actually exists; writing that runbook speculatively now would itself be the kind of premature multi-project machinery the Non-Goals forbid.

3. **Bidirectional Notion-to-queue intake.** v1 treats the Notion mirror as strictly read-only/Derived. Letting Gabriel enqueue new work by adding a row to an Ops Hub view (an intake script that materializes a `task.json` from it) is deferred: it requires solving safe handling of non-atomic Notion reads as a trusted *input* to the queue (not just an output), a materially different and harder problem than the read-mostly mirror v1 ships, and it isn't needed while Code can create tasks directly.

4. **Conflict-copy auto-reconciliation.** v1 treats any OneDrive conflict-copy file found during lease acquisition as fail-closed `LeaseContested`, requiring human resolution every time. A heuristic that auto-reconciles the obvious cases (byte-identical content, or an unambiguous timestamp winner) is deferred until there is real operational data on how often conflicts actually occur — failing closed to a human is the correct default in the absence of that data, not a stopgap to be embarrassed about.

5. **Second-workstation / cross-machine leasing.** The whole locking model (atomic-exclusive-create plus a 30-second settle-and-rescan) assumes exactly one physical machine, which is a current Non-Goal. This is flagged explicitly as the first design assumption to reopen if ORA ever adds a second workstation, because the atomicity guarantees the lock manager relies on change materially once two independent filesystems are involved instead of one shared OneDrive-synced volume.

6. **A sixth `escalation.schema.json`.** The human-escalation row (AAOS-SPEC.md §10: `escalation_id`, `severity`, `trigger`, etc.) is as structured as any of the five contract-first schemas and is referenced from `event.json`'s `refs.escalation`, but the master prompt named exactly five schemas and escalation rows are a Notion-native, human-facing artifact rather than agent-to-agent coordination state — so it was deliberately left outside `tools/validate.py`'s JSON-Schema-checked contract set for v1 (flagged in the Phase 1 design review, see `PHASE1-DESIGN-REVIEW.md` finding #3). If escalation volume or drift ever makes this painful in practice, formalizing it as a sixth schema is the fix; not needed to ship v1.
